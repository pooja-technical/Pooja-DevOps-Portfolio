PROJECT 01 / AWS / CLOUD

AWS 3-Tier
Architecture

Designed and implemented a three-tier application architecture on AWS using separate layers for presentation, application processing and database services.

AWS VPC EC2 ALB Target Group Auto Scaling RDS NAT Gateway Networking

Project Objective

The objective was to understand how a scalable and secure application can be structured on AWS by separating the presentation, application and database layers.

The architecture was designed to isolate resources into appropriate network layers while allowing controlled communication between them.

What I Built

🌐 VPC

Created a dedicated AWS VPC to provide an isolated network environment for the application architecture.

⚖️ Application Load Balancer

Used an Application Load Balancer to receive incoming application traffic and distribute requests to registered targets through a Target Group.

🎯 Target Group

Used a Target Group to maintain the set of registered application targets and perform health checks before routing traffic to healthy targets.

💻 EC2

Used EC2 instances to host the application layer. Application instances are designed to remain private and receive traffic through the load balancer.

📈 Auto Scaling Group

Used an Auto Scaling Group to manage EC2 capacity according to defined scaling policies and maintain the desired number of instances.

📋 Launch Template

Used a Launch Template to define the configuration required when new EC2 instances are launched, including AMI, instance configuration and user data.

🚪 NAT Gateway

Designed private application resources to use a NAT Gateway for required outbound internet connectivity without assigning public IP addresses to the EC2 instances.

🗄️ RDS

Used Amazon RDS as the database layer and designed database access to be restricted to the application layer rather than exposing the database directly to the internet.

Networking & Security

  • Designed public and private subnet layers based on resource accessibility requirements.
  • Used an Internet Gateway to provide internet connectivity for resources requiring public access.
  • Designed private application resources to use a NAT Gateway for required outbound internet connectivity.
  • Restricted EC2 inbound application traffic to the Application Load Balancer security group.
  • Restricted database inbound traffic to the application EC2 security group.
  • Used Security Group references instead of relying on individual resource IP addresses for communication between application layers.
  • Applied the principle of allowing only required communication between components.

Scalability & Availability

The application layer can be managed through an Auto Scaling Group. Scaling policies can increase or decrease the desired capacity based on defined conditions such as CPU utilization.

A multi-Availability-Zone design can improve availability by distributing resources across separate Availability Zones. If one Availability Zone experiences an infrastructure failure, resources in another Availability Zone can continue serving the application.

Troubleshooting Approach

During AWS troubleshooting practice, I learned to approach connectivity problems layer by layer instead of checking components randomly.

01. ALB Listener

Verify that the listener is configured correctly for the expected protocol and port.

02. Target Group

Verify that the EC2 instance is registered with the correct Target Group.

03. Target Health

Check whether the target is healthy and review the configured health-check path, port and protocol.

04. Security Groups

Verify that the EC2 Security Group allows the required application traffic from the ALB Security Group.

05. EC2 Status

Verify that the EC2 instance is running and passing its instance status checks.

06. Application Port

Verify that the application is running and listening on the port configured in the Target Group.

07. Network Configuration

If required, inspect route tables and Network ACLs for rules that could prevent communication.
